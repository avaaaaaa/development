* Web Components allow us to create our own custom reusable HTML elements
they will then encapsulate all the styles, logic & functionality so that it becomes reusable
You'd then be able to use this web component anywhere in your app by using it the same way you use HTML Elements

Here's how your app would look like when using Components
(whether Web components or Components created with a front-end library/framework):

<app-root>
   <app-navbar page="home"></app-navbar>
   <flashcards-questions>
       <flashcards-question></flashcards-question>
       <flashcards-question></flashcards-question>
       <flashcards-question></flashcards-question>
   </flashcards-questions>
   <app-sidebar></app-sidebar>
</app-root>

Web components are:
    reusable: you can reuse a component as many times as you want
    modular: they're based on modules. The definition of a web component is most often in a single file. This makes it easier to maintain as you know where to find the logic of a specific web component
    encapsulated: they hide the implementation detail so that you can focus on what matters.

You can use Web Components in parallel with components generated by most front-end frameworks support.
see: https://custom-elements-everywhere.com/

they work on all modern browsers
This is quite important because, unlike front-end frameworks/libraries, they are baked into the browser.

While you don't necessarily need a library to use them, a small library would make life easier when working with Web Components.
because Web Components are low-level browser APIs
	they are powerful but requires more coding
	This is why there is an excellent high-level abstraction library on top of Web Components which is Lit
		see: https://lit.dev/
However, since the core technology is baked into the browser, the size of web component libraries tend to be small.

There are 4 main standards involved in the creation of Web Components. These are:
    ES Modules
    HTML Templates
    Shadow DOM
    Custom Elements


* creating custom elemets
The Custom Elements API allows you to define your own DOM element.
let's say we want to create a custom <app-navbar> element, here's the minimum necessary code for it to work:


class AppNavbar extends HTMLElement {
	// implementation of logic & style etc.
}

window.customElements.define("app-navbar", AppNavbar);


with the code above, we can use <app-navbar></app-navbar> in our html file(s)
window.customElements.define() instructs the browser that we are creating a new custom element.
This requires two arguments: the name of the element and the class describing it.

In our example, we defined a new custom element, app-navbar
(which means the web component will be available as <app-navbar></app-navbar>),
and its class definition is AppNavbar.

When naming your component, you have to choose a name that contains a hyphen (-) in it.
This is because names that are made up of 1 word are reserved for the browser. For example, p, div, span, address, table, etc.
On the other hand, names made up of more than one word (so, separated by a -) are up to the developer to define.

You can name the class however you want; however, we recommend naming it an uppercased version of the custom element name.
For example:
    <app-navbar> would have a class AppNavbar
    <my-navbar> would have a class MyNavbar

If you define your own constructor method, you will need to call super() first thing as we are extending from HTMLElement.
otherwise, an error will be thrown


class AppNavbar extends HTMLElement {
    constructor(){
        super(); // ALWAYS start with super()
    }
}

window.customElements.define("app-navbar", AppNavbar);


* shadow DOM
after creating the custom element, We will attach the Shadow DOM
with shadow DOM, we can encapsulate styles & scripts.
A Shadow DOM is a portion of the DOM that is encapsulated from the rest of the DOM.
This means styles & scripts are self-contained inside this shadow DOM.
external CSS won't bleed into the Shadow DOM, and CSS within the shadow DOM won't leak to the outside
	this is also called shadow boundaries


<style>
    p {
        color: red;
    }
</style>
<p>Page subtitle</p>
<dashboard-stats>
    <!-- Shadow DOM starts here -->
    <p>Dashboard stats</p>
    <!-- Shadow DOM ends here -->
</dashboard-stats>


Only the <p>Page subtitle</p> will have a color: red;
whereas the <p>Dashboard stats</p> will not!
That's because styles do not go in or out of the Shadow DOM.
you can now write CSS that is scoped to a certain component without having to worry about how it will affect other elements on the page


<dashboard-stats>
    <!-- Shadow DOM starts here -->
    <style>
        p {
            font-weight: bold;
        }
    </style>
    <p>Dashboard stats</p>
    <!-- Shadow DOM ends here -->
</dashboard-stats>


Only the paragraphs (<p> elements) inside the <dashboard-stats> component will be in bold.
But paragraphs outside this component or in other components will not be affected.


** attaching shadow
class AppNavbar extends HTMLElement {
    constructor(){
        super(); // ALWAYS start with super()
        this.attachShadow({mode: "open"});  // attaching the shadow DOM
    }
}

window.customElements.define("app-navbar", AppNavbar);


Most (if not all) Web Components you're going to create will have a mode: "open".
This means you can still access this Web Component using JavaScript from the outside.
We almost never want to prevent that.
If, for some reason, you want to prevent that, then you can do so with mode: "closed".
if you want to inspect the shadow DOM
	const shadowRoot = this.attachShadow({mode: "open"});
	console.log(shadowRoot);


** constructor(), connectedCallback(), disconnectedCallback()
When the element is created, the constructor() is called.
	This is often used to attach the shadow root.
	You should not make any DOM manipulations at this stage
		It's better to make these in the connectedCallback()

When the element is inserted into the DOM, the connectedCallback() is called.
	it is called as soon as the element is inserted into the DOM.
	This is where you'd do DOM operations because the element is now inserted into the DOM.
	This is where you'll most likely manage attributes and add event listeners.
	it is recommended to manipulate the content of the custom element in the connectedCallback() only.

When the element is removed from the DOM, the disconnectedCallback() is called.
	it is called when the element is removed from the DOM.
	This is often used to clean up and restore memory.
	Most commonly, it's used to remove event listeners that you have added in the connectedCallback().

Note that these methods will only be called if you define them.


class AppDashboard extends HTMLElement {
    constructor() {
        super();
        console.log("AppDashboard created");
        this.attachShadow({mode: "open"});
    }

    connectedCallback() {
        console.log("AppDashboard inserted into DOM");
        // add event listeners (if necessary)
    }

    disconnectedCallback() {
        console.log("AppDashboard removed from DOM");
        // remove event listeners (that were added in connectedCallback())
    }
}

window.customElements.define("app-dashboard", AppDashboard);

const element = document.createElement("app-dashboard");
	// "AppDashboard created" will be logged
document.body.appendChild(element);
	// "AppDashboard inserted into DOM" will be logged


** HTML templates
An HTML template (<template>) lets you define the code (mostly HTML & CSS) of a Web Component.
HTML Templates do not render until they're appended into an element.

creating the template (within <body></body>):
<template id="dashboard-template">
    <style>
        p {
            font-weight: bold;
        }
    </style>
    <p>Dashboard stats</p>
</template>

using the template:
class DashboardStats extends HTMLElement {
    constructor() {
        super(); 
        this.attachShadow({mode: "open"});
    }

    connectedCallback() {
        const template = document.querySelector("#dashboard-template");
        this.shadowRoot.appendChild(template.content.cloneNode(true));
        // This will add the HTML received from the template into the shadow root of the custom element.
    }
}
window.customElements.define("dashboard-stats", DashboardStats);


cloneNode():
	The reason why we need to clone it is that the template can only be used once.
	Cloning it will allow you to use it another time in the future.
	it accepts one parameter "deep".
		Calling cloneNode(true) sets the deep parameter to true which will clone children elements too.

You may be thinking that there's a lot of code necessary to set this up and you are right.
This is one of the reasons why it's often recommended to use a Web Components library such as lit.
